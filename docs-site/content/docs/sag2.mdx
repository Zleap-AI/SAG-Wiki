## SAG2 是什么

SAG2 是 SAG Wiki 使用的检索方法。它从本地原始文档中寻找回答问题所需的证据，可以根据已找到的内容继续检索其他文件。结果仍然指向原文，便于查看上下文和核对来源。

它在建库时保存原文和全文索引，不预先计算向量，也不调用 LLM 提取文档关系。检索时先按词项找到候选片段，再判断哪些片段真正提供证据，并从这些原文中提取新的查找词。

## 一次检索如何进行

<RetrievalDiagram lang="zh" />

**候选**是先找到、等待判断的原文片段；**证据**是能支持回答中某个事实的内容。BM25 按词项匹配得到候选，Jev 结合问题和已有材料判断证据价值。

1. **从本地索引召回候选。** 使用问题中的词项，从全文索引中找到初始原文片段。
2. **由 Jev 判断证据价值。** 针对原问题评估每个候选是否提供必要事实，同时检查实体与关系是否一致。仅主题相关的背景内容不等于必要证据。
3. **从候选中扩展检索。** 选取评分靠前且尚未扩展的片段，从中提取词项和完整名称，再检索新的候选。
4. **结合已找到的证据重新评分。** 后续判断可参考前面找到的证据，但不能把其他片段里的事实误算为当前片段的证据。
5. **本地整理并返回原文。** 排序和结果多样性处理在本地完成，保留文件路径及原文位置。

SAG Wiki 默认进行首次召回加 1 次扩展，共最多 2 轮检索。没有新候选或扩展词时会提前结束；设置最多允许扩展 2 次。论文实验默认最多扩展 2 次，与应用默认设置不同。

## 为什么需要跨文件检索

例如，你问“登录后，系统如何确定用户能访问哪些接口？”。登录流程、角色配置和接口检查可能分别写在不同文件中。找到第一份文件后，其中出现的名称或标识可以成为下一次查找的词项。

<EvidenceDiagram lang="zh" />

这里的“多跳”指通过中间事实继续查找：先知道登录会话使用哪个角色，再找这个角色有哪些权限，最后确认接口如何检查权限。每一步仍然需要原文支持，不能仅凭词语相同就认定结论成立。

## Jev 与回答模型的区别

| 部分 | 负责什么 | 是否生成最终回答 |
| --- | --- | --- |
| 本地索引 | 文档处理、全文索引、候选召回、扩展词统计与本地排序 | 否 |
| Jev | 判断原文是否为问题提供必要证据 | 否 |
| 回答模型（LLM） | 根据问题和检索到的材料组织回答、调用可用工具 | 是 |

**建库不调用 LLM；SAG2 的检索流程不调用回答 LLM，但会调用你配置的 Jev 判断服务。** 使用问答或搜索自动总结时，才会另外调用回答模型。因此，“检索不使用回答 LLM”不代表深入检索完全离线或无需服务配置。

## 与快速搜索如何配合

- 已知名称、词语或错误信息：先用快速搜索，或通过 CLI 的固定字符串、正则匹配查找。
- 需要按完整问题查证、连接多份文档：使用 SAG2 深入检索。
- 需要一段带引用的完整回答：进入问答，由回答模型调用检索并生成答案。

更完整的证据有助于回答，但检索结果不构成正确性保证。重要结论仍需查看原文及适用条件。

## 为什么可以减少 Agent 上下文

Agent 可以通过 `sag "完整问题"` 获取相关原文片段、文件路径和位置，再按需阅读。这样可以减少一次性读取大量无关文件的需要。

实际 Token 消耗、耗时和检索效果取决于资料、问题、参数和 Agent 后续行为。这里不承诺固定的节省比例。

## 哪些参数可以调整

[搜索设置](/zh/docs/search#搜索设置详解)控制候选数量、扩展起点、扩展词、轮数、返回片段和切分长度。候选与轮数增大通常会增加工作量；返回片段数量控制最终输出，不等于候选召回数量。

同一轮评分可能因候选大小被拆成多个请求，所以“1 次工具调用”“1 轮检索”和“1 次 Jev 请求”是不同计数。

## 研究与实现

SAG Wiki 基于 SAG2 方法，但桌面搜索、问答和 CLI 会按各自输出需求组织结果。基准任务的分数不等于任意本地资料上的保证。
