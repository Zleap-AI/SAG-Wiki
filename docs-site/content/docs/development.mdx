## 环境

需要 Node.js、npm、Rust 和目标平台的 Tauri 开发依赖。前端依赖通过 `package-lock.json` 固定，Rust 依赖通过各 crate 的 `Cargo.lock` 固定。

仓库包含五个 Rust 构建入口：`protocol/`、`client/`、`core/`、`cli/`、`src-tauri/`。修改共享逻辑时，在 `core/` 中实现，避免在桌面和 CLI 中各写一份。

## 从源码运行桌面应用

在仓库根目录执行：

```sh
npm ci
npm run tauri dev
```

Tauri 开发命令会先构建 debug CLI，再启动 Vite 和桌面后端。前端改动使用热更新；Rust 改动需要重新编译后端。日常界面开发不需要反复生成安装包。

桌面开发服务不监听 `.cache/`、`docs-site/` 和 `browser-extension/build/`，文档及扩展构建不会触发桌面窗口刷新。

只启动前端开发服务器：

```sh
npm run dev
```

前端服务器不能替代 Tauri 的本地文件与检索接口。验证完整桌面流程时使用 Tauri 开发入口。

## 构建 CLI

```sh
npm run build:cli:dev
npm run build:cli
```

前者生成 debug CLI，后者生成 release CLI。开发产物放在 `src-tauri/bin/development/`，正式产物放在 `src-tauri/bin/`；macOS 产物会执行签名步骤。

桌面端和 CLI 打包时，会从仓库的 `third-party/pdfium/` 读取对应平台的 PDFium 压缩包，校验 SHA-256 后将运行库和许可文件放入安装包。这个步骤无需联网下载 PDFium。

需要把当前构建安装到用户终端时，显式执行：

```sh
./src-tauri/bin/sag install cli
sag --version
```

安装器检查归属、校验值和构建渠道，以暂存文件校验后原子替换。开发桌面不自动更新正式 CLI；开发 CLI 也拒绝覆盖已登记的正式安装。Rust 源码变更后重新执行 `npm run build:cli:dev`，让桌面和服务使用相同构建身份，再重新启动桌面。

## 构建桌面应用

```sh
npm run build
npm run tauri build
```

Windows 使用：

```sh
npm run package:windows
```

使用目标平台对应的系统依赖和签名配置。可分发产物与原生 CLI 来自同一版本源码。npm 分发见[npm 发布](https://github.com/Zleap-AI/SAG-Wiki/blob/main/docs/zh-CN/npm发布说明.md)。

## 代码检查

```sh
npm run check
npm test
cargo test --manifest-path protocol/Cargo.toml
cargo test --manifest-path client/Cargo.toml
cargo test --manifest-path core/Cargo.toml
cargo test --manifest-path cli/Cargo.toml
cargo test --manifest-path src-tauri/Cargo.toml --lib
```

桌面构建与检查依赖本地 CLI 资源时，先执行 `npm run build:cli:dev`。用独立数据目录进行手动开发检查，避免影响日常知识库：

```sh
SAG_DATA_DIR=/path/to/dev-data npm run tauri dev
SAG_DATA_DIR=/path/to/dev-data ./src-tauri/bin/development/sag service status
```

桌面与 CLI 共用同一份开发数据时，设置相同的 `SAG_DATA_DIR`。服务退出后会按需启动，macOS 退出桌面客户端后保留服务，Windows 从托盘或应用菜单退出时停止服务；测试结束可执行 `sag service stop`。需要模型服务的功能使用开发者自行配置的凭据；纯索引和本地匹配不需要 API 密钥。

## 文档与仓库边界

`docs/` 保存当前架构、开发指南、接口说明与明确标记的设计计划。实现变化时更新相应文档，避免追加多份相互冲突的历史说明。

开发产物、临时输出、日志、截图和本地数据不提交到文档目录。凭据与用户知识库不进入发布包。自动化测试代码及必要 fixture 保留在各自的测试目录。

## 网页剪藏扩展

运行 `npm run build:clipper` 构建 Chrome / Edge 扩展包，产物位于 `src-tauri/clipper/`。macOS 安装完整 Xcode 后，可运行 `npm run build:clipper:safari` 构建 Safari 本地测试应用，产物位于 `browser-extension/build/`。测试版使用独立的 `com.sag.webclipper.development` 标识，避免干扰已安装的正式扩展。

准备正式 Safari 应用时，运行 `node browser-extension/build.mjs --safari --release`，再完成应用和 DMG 的签名、公证。macOS 桌面端构建使用 `src-tauri/clipper/sag-web-clipper-safari.dmg` 中已公证的安装包，也可通过 `SAG_CLIPPER_SAFARI_DMG` 指定路径；校验未通过时停止构建。桌面端构建不会用未签名测试包覆盖正式包。

## 下一版发布准备

改动说明见[更新日志](/zh/docs/updates)。安装包以最新正式发布为准。发布前须在同一提交上通过前端、文档及 macOS/Windows 构建，并核对安装升级、已有索引保留、分阶段状态和失败重试；标签与桌面端、CLI 版本必须一致。

产品 PR 合并前须在 `CHANGELOG.md` 的明确版本号标题（如 `## 0.3.4`）下追加面向用户的中文变更条目，并在 `### English` 下按相同顺序追加对应英文条目；每项使用单行 `- ` 列表。已发布条目保留在实际发布版本下，不使用未发布占位标题。PR 检查会拒绝产品改动缺少、未更新或仍使用占位标题的发布说明；明确标记 `release:skip` 的内部改动除外，纯文档、CI 和发布工具改动无需产品条目。版本记录只编辑根目录 `CHANGELOG.md`，运行 `npm --prefix docs-site run changelog:generate` 生成双语更新日志，不直接修改生成页。`npm --prefix docs-site run changelog:lint` 在所有 PR 中检查所有版本，纯文档 PR 也不跳过；PR 检查、新标签准备和草稿正式发布会拒绝缺失或不一致的条目，文档构建成功不能替代此检查。 `docs-site` 可单独构建，不依赖上层目录或 Git。完整仓库的发布流程先运行 `node scripts/documentation-release.mjs build`，再构建文档，产物包含 `docs-version.json`。实际部署后检出预期提交，运行 `npm --prefix docs-site run verify:deployment -- --url https://your-docs-host.example --expected-sha <完整提交SHA> --release v0.3.5`，核对版本信息与双语页面内容标记。此命令供实际部署流程调用，不引入托管平台或桌面新版本。

功能条目后可附对应的 Issue 和 PR Markdown 链接，例如 `修复公式显示。（[PR #142](https://github.com/Zleap-AI/SAG-Wiki/pull/142)）`；中英文条目均可保留这些链接。链接用于关联改动，不能代替功能描述；仍禁止提交标题、提交哈希和提交链接。

编写条目前先获取远程版本标签，以自动流程计算的下一版本号建立标题；版本冲突时在合并前调整标题。自动准备沿用该版本的已审核说明，并在独立发布提交中统一应用、CLI 和锁文件的版本，不改写主分支的日志标题。说明缺失或格式无效时，在创建 tag 前停止。应用内更新提示仅包含中英文功能改动；GitHub 发布页另附 Windows x64、Apple Silicon 和 Intel 安装包下载表。不生成提交标题、提交引用、自动发布套话或签名迁移附加段落。

## 自动构建与发布

main 的产品改动自动准备一致的版本元数据，生成发布子提交和 tag，完成必要检查后自动签名、公证并正式发布。纯文档、CI 和发布工具调整不发版，不需要逐版人工审批。Rust 原生测试与正式编译保持并行；macOS 安装包构建与包内检查通过后即可签名，不等待 Rust 测试，最终发布仍要求三个平台、前端、文档及制品检查通过。重试接续同一版本和已验证阶段。现有仓库须由管理员一次性迁移 release 环境后启用自动发布，详见[发布与恢复指南](https://github.com/Zleap-AI/SAG-Wiki/blob/main/docs/zh-CN/应用内更新发布.md)。


发布效率：前端资源在同一源码上构建一次，供 Windows x64、Apple Silicon 和 Intel 安装包共享；本地构建仍可独立执行。两个 Mac 签名任务分别等待各自构建完成，不占用 Mac 运行器轮询，也不等待其他平台。原生构建仅暂存 App 归档，签名阶段才制作最终 DMG；旧版含临时 DMG 的检查点仍可恢复。正式发布不再额外构建 Safari 开发安装包；Safari 原生保存测试仍保留。签名后的更新包与 DMG 保留内容、身份、票据和签名校验，相同二进制只执行一次完整 Jev E2E。

原生 Rust 测试仅在全部原生源码、测试、依赖、配置及编译环境与上一成功正式版一致，且已核实该版三平台原生任务全部成功时复用。输入有变化、基线不可验证或查询失败时，三平台均运行完整原生单元与集成测试；Python、Safari 原生保存和最终生产安装包检查仍执行。排除不参与安装包的性能探针示例编译，并避免重复执行同一 CLI 进程回归测试。复用结果的轻量任务在 Ubuntu 上记录，不申请 Mac 运行器；Python 和 Safari 原生保存检查在对应平台的生产构建中执行。不增加必需检查或审批。

每次正式 Release 都包含 Windows x64 EXE、Apple Silicon DMG 和 Intel DMG，以及相应更新资源；任一平台缺失时，现有组装和发布检查会阻止发布。Release 正文直接列出三个安装包下载链接；应用内更新说明仍只显示功能变更。

可信 tag 任务会导出仅包含 Rust 依赖的缓存，供后续版本复用，并校验仓库、源码、最新任务 attempt、兼容性和摘要。缓存排除应用与测试可执行文件、本地 SAG 库，保留 14 天；兼容键只忽略本地包版本变化。缓存未命中时正常编译，全部必要测试和安装包检查继续执行。分支 CI 使用独立验证命名空间测量归档开销，不签名或发布。

依赖归档使用运行器已有的 zstd 多线程压缩和流式 tar 读写；恢复时先完整校验暂存内容与解压进程结果，再原子替换依赖文件。缓存失败时仍正常编译。

每个平台的 CLI 与桌面正式编译在独立运行器上并行，打包前汇合已验证输入。编译阶段的资源处理保留原有嵌入配置，实际安装包包含经验证的 CLI 和 QPDF 资源，并保留全部安装包及 CLI 检查；macOS 不等待 Windows。生产任务执行次数与缓存角色保持隔离。测试编译配置通过手动配对 A/B 工作流测量，保留具名测试、忽略状态、断言和溢出检查，不改变正式产物的优化配置。

PR E2E 与 Desktop 的外层测试并发预算统一为 2；独立 CLI 并发场景仍启动 20 个客户端进程，生产服务的启动等待期限保持不变。

Rust 编译配置的手动工作流支持 `comparison=cgu-only` 与 `platform=macos`，可保持 debug=1，仅比较 CGU16/64。采用配置前须完成三轮同运行器配对测量，并比较完整编译与测试执行耗时。

Desktop 原生测试保留现有 debug=1、非增量 CGU16 基线：已测候选尚未证明编译加测试执行有实质且稳定的净收益。正式产物的优化配置保持不变。

内部整理或构建改动无需单独发版时，在合并前给 PR 添加 `release:skip`。必要检查照常执行；本次 main 推送的产品提交全部属于带标签的已合并 PR 时，自动准备才跳过打 tag 和发布。混合推送含普通功能 PR 时正常发布，查询失败则停止准备。支持 merge/squash/rebase；后续功能版本包含积累的改动。标签不撤销已准备的发布，不影响显式 tag 或手动发布。

若 GitHub 尚未更新合并关联，或产品推送无法唯一核实已合并 PR（例如直接推送），准备流程停止且不创建 tag。关联更新后可重试；仍可显式手动发布。
