# DigUp 与 SAG 检索方案对比

核对日期：2026-11-03。

范围：前半部分核对 DigUp，后半部分核对 SAG 当前实现并比较取舍。DigUp 读取 `/tmp/digup-inspect.ZiPQOa`，锁定提交 [`dc2651ad8299160bbe91e972f857e1a1599a8419`](https://github.com/ARahim3/DigUp/commit/dc2651ad8299160bbe91e972f857e1a1599a8419)。相关行为以该提交为准，不代表后续版本。

方法：静态阅读源码、测试代码、公开查询集和仓库内说明；联网确认固定提交的源码页面。**未运行模型、应用、测试或检索评测，所有速度、内存和准确率数字均未实测。** 仅统计了 JSON 查询条数。文中的“代码推导”指由分支条件直接推出的行为；“项目方报告”指源码注释或网站中的测量声明。

## 1. 扫描、增量更新与资源

### 初次扫描和增量更新

- 扫描先枚举选中目录，记录路径、类型、大小、修改时间、设备号和 inode，再同步 SQLite。新文件入库时就写入文件名及目录关键词；模型未下载完成时也能先查文件名。[D01] [D02] [D03] [D37]
- 默认处理顺序为截图、图片、PDF、文档、音频、视频，各类内部按修改时间倒序；同类图片或截图最多八张一批，其余按文件处理。文件读取与模型计算并行一个批次，已完成批次陆续入库。[D04] [D05] [D47]
- 增量判断依据为大小、修改时间差超过 0.001 秒或文件类型变化。变化文件先删除原内容片段再重新处理，保留文件名记录；没有按内容哈希或片段差异更新。因此大小、修改时间和类型均不变的内容改写，单凭这条同步逻辑无法发现。[D01] [D02]
- 同一次扫描范围内，新旧路径具有相同设备号、inode、大小和近似修改时间时，识别为移动或改名，只更新路径及文件名关键词，不重算向量。相应地，曾作为模型输入的旧标题或路径不会因此重算。[D01] [D02] [D12]
- 删除或新排除的文件移出索引。索引服务先排除不可用目录；扫描途中消失的根目录也有保留原记录的处理。[D01] [D03]

macOS 目录监听会触发再次扫描，普通文件变化合并等待 0.75 秒；这仍然重新枚举选中目录，再判断哪些文件需要重算。代码目录默认静默 60 秒后同步，持续变化时最长等待 600 秒。一次同步新增或变化不超过 50 个文件时，进入优先队列；历史待处理文件及长文件后续部分受后台处理条件控制。上述时间是调度参数，不是完成耗时保证。[D03] [D06] [D07]

### 长文件分阶段

| 类型 | 首次处理 | 后续处理和上限 |
| --- | --- | --- |
| PDF | 不超过 50 页的一次处理；超过 50 页的先处理前 30 页 | 每步 30 页，最多 5,000 页 |
| 普通文档 | 先处理前 40 个片段 | 每步 40 个片段，最多 5,000 个片段 |
| 音频、视频 | 按窗口或帧生成多个向量 | 没有采用 PDF、文档的 `partial` 后续阶段流程 |

这些是默认值。长文件记录 `partial`、`read_to` 和 `read_end`；主索引和代码索引没有待处理文件后，再处理长文件剩余部分。每步独立提交，暂停后可以从已提交位置继续。文档在每一步会重新读取全文并切分，再取当前范围，不能理解为文件读取本身也只读取新增片段。[D05] [D08]

“已完成”也不必然表示全文覆盖：达到 5,000 页或片段上限时，保存上限说明并标为 `done`；后续读取出错时，保留已存内容、记录停止原因，也可以标为 `done`。[D08]

### 资源释放

索引工作在独立进程内运行。默认处理结束后保留模型 60 秒等待新任务，再退出；文件解码框架的进程内缓存也随退出释放。批次使用临时目录，完成后删除；服务还清理已退出进程遗留的临时目录。macOS 查询编码器默认闲置 600 秒后关闭，并释放主索引与代码索引的内存向量；Windows/Linux 查询服务默认 300 秒释放编码器和向量，600 秒退出服务进程。关键词索引可在不加载向量时使用。[D03] [D07] [D09] [D10]

索引进程另有监控：默认内存阈值为机器内存一半，限制在 4–8 GiB；单次文件读取超过 15 分钟会终止进程并记录文件。后续服务将该文件标为失败，或保留长文件已完成部分。它监测的是整个索引进程内存及当前读取时间，不能等同于每个模型请求都有超时。[D11]

### 预计耗时

估算使用文件数、PDF 页数、媒体时长、文档字节数和代码大小，分别估计首次处理与后续长文件处理。文档片段数按约 `文件字节数 / 2000` 估算，并未先抽取正文核实。macOS 优先使用系统元数据，缺失时读取 PDF 或媒体信息。[D13] [D14]

默认成本来自项目方报告的 M4 Pro 测量，例如图片 0.12 秒/张、截图 0.32 秒/张、PDF 0.09 秒/页、文档 0.045 秒/片段。程序把实际索引成本记入 `costs.json`；某类样本达到门槛后改用本机平均耗时，例如图片/截图各 20 张、PDF/文档各 30 个单位、音视频各 600 秒、代码 100 个片段。统计量过大时折半历史累计值；首次模型启动不计入该批次成本。[D05] [D13] [D15]

这些机制支持本机修正估算，但无法从源码确认用户目录的耗时或误差范围。压缩文档的字节数、扫描页比例、视频变化程度、设备和当时负载都会影响实际工作量；固定成本不应转述为所有设备的速度。[D08] [D13] [D15] [D19]

## 2. 多模态粒度、存储和评分

### 模型和内容粒度

默认模型为 `google/embeddinggemma-2` 的 Q8_0 GGUF 转换，下载仓库为 `ggml-org/embeddinggemma-2-GGUF`，固定 revision 为 `bfcd298762cc34d0357ece5ebdd31791a3a374d8`。运行时为 llama.cpp；Python mlx-vlm worker 是可选参考实现。各输入输出 768 维向量，单次输入内部采用均值池化及 L2 归一化。[D16] [D17] [D41]

| 内容 | 实际向量粒度 | 关键词和定位 |
| --- | --- | --- |
| 图片、截图 | 每张图片一个图像向量；默认视觉 token 预算分别为 140、280 | 文件名及目录可查；截图在 macOS 另做 OCR，只用于关键词，没有额外 OCR 文本向量 |
| PDF | 通常每页一个文本向量；文字不足 200 字符时转为图像向量，预算 280 | 保存页码和可用正文；macOS 可用 OCR 补充扫描页关键词。部分乱码页有图像向量加乱码文本向量的特殊路径 |
| 普通文档、表格、幻灯片 | 抽取成文本后按约 1,800 个 Swift 字符切分；尝试在空白处断开，重叠目标 200 字符 | 保存各片段正文及片段序号；并非每张表格或幻灯片固定一个向量 |
| 音频 | 16 kHz 单声道，30 秒窗口、25 秒步长；过滤静音窗口 | 保存起止秒数；这条索引流程不生成可供关键词搜索的转写文本 |
| 视频 | 图像帧向量与音轨窗口向量分别保存 | 保存帧或音频窗口的时间；默认采样间隔为 `max(3 秒, 总时长/1200)`，再过滤近重复帧 |
| 代码 | 约 1,800 字符的完整行片段，Notebook 按单元格组合 | 保存行号或单元格号；详见第 3 节 |

表中均指满足生成向量条件且处理成功的输入。图片/PDF/文档落库路径见 [D08] [D12]；音视频窗口、静音过滤和帧采样见 [D18] [D19]。视频近重复判定使用 8×8 平均哈希，与上一保留帧相差不超过四位则跳过；这是图像去重规则，不能据此保证每个真实镜头都有代表帧。[D19]

普通文档切分使用字符和空白，未按模型 tokenizer 切块；无空白时，目标重叠不一定保留。PDF 文本模型输入只取该页正文前 4,000 字符，全文仍可进入关键词索引。llama.cpp 路径还会把索引文本输入截到 2,048 tokens，专用查询编码器截到 512 tokens，均包含提示词和特殊 token。因此分阶段完成文件，不代表每页、每片段的所有字符都进入了向量。[D08] [D12] [D17]

### 向量存储与匹配

`index.sqlite` 保存文件、片段、位置、摘要、向量和 FTS5 关键词索引；`code.sqlite` 单独保存代码。向量按 768 个 Float16 存为 BLOB，原始向量数据每行 1,536 字节，数据库还有文本和其他开销。[D20]

搜索时把全部非空向量加载到内存，仍保存为 Float16；每次查询每 1,024 行转换为 Float32，计算矩阵与查询向量的点积。因输入已归一化，点积用于近似原始余弦相似度，存在半精度存储误差。当前路径没有 HNSW、IVF 或其他近似候选索引；计算量随向量条数增加。macOS 使用 Accelerate，Windows/Linux 使用 SIMD 循环。内存向量通过匿名 `mmap` 或 Windows `VirtualAlloc` 分配，释放时取消映射；这里没有把 SQLite 向量文件直接当作外部向量数据库。[D17] [D21] [D22] [D38] [D39] [D42]

每个片段先获得调整后的语义分数，同一文件只保留最高分片段。没有把文件内所有片段向量平均为整篇向量。结果优先定位到达到语义阈值的片段，否则使用关键词命中片段；代码还有额外定义位置查找。[D23]

### 关键词融合

关键词检索使用 FTS5，按 `bm25(fts, 3.0, 1.0)` 获取最多 1,000 个片段候选，再保留最多 100 个不同文件。对这些文件计算查询词覆盖率 `c`：查询模式中有多少比例能在文件任意片段找到。覆盖率可以来自不同片段。[D23]

默认候选条件及评分为：

```text
候选：文件最佳语义分 z ≥ 2，或者关键词覆盖率 c ≥ 0.5
普通检索：score = max(z, 0) + 2 × c^1.5 + 类型加分
代码检索：score = max(z, 0) + 1 × c^1.5 + 类型加分
编号或标识符查找：语义权重变为 0.5，当前关键词权重乘 2
类型加分：查询包含已识别文件类型词且与文件类型一致时，加 1
```

BM25 影响关键词候选及次序，其数值不直接进入最终融合公式；当前公式也不采用倒数排名融合。只有至少四位的纯数字、包含数字的代码等符合特定规则时，才按编号查找处理，不能概括为所有精确短语都加倍。最终分数用于排序，不是正确概率。低于首项分数一半的结果折叠显示，仍属于返回结果。[D23] [D24]

### 跨模态分数校准

每个查询都会计算全部向量的相似度分布。对文本、图片、音频分别求均值；某模态参与统计的向量少于 20 个时，用总体均值。先减对应均值，再对居中后的全部统计样本计算共同均值和标准差，标准差下限为 0.02，最后得到 `z`。各模态没有分别除以各自标准差。[D25]

后续阶段加入的长文档片段仍参与检索，但不参与上述均值和标准差统计。PDF 超过 50 页时，第 30 页之后的页片段不参与；普通文档第 40 片段之后不参与。代码使用默认 `IndexOptions()` 判定这些边界。这是一种依赖当前索引分布的排序调整，不能解释为经过独立标注集训练的概率校准，也不能把不同查询的 `z` 直接当作同一准确率。[D21] [D25]

## 3. 忽略规则、独立代码索引和位置

### 普通索引的过滤

枚举跳过隐藏内容、应用包，另排除依赖目录、`.noindex`、带有效 `CACHEDIR.TAG` 的缓存目录、macOS 的 `~/Library`，以及用户指定目录和扩展名；未下载的云端占位文件及符号链接不读入。[D01] [D26]

普通索引默认不读代码及数据扩展名。遍历途中发现 `.git`、`package.json`、`pyproject.toml` 等项目标记后，该项目内只保留截图；用户直接选择为根的目录不会仅因自身带项目标记被整块排除，但仍受类型等其他规则约束。[D01] [D14] [D26]

数据集过滤也是启发式：非用户直接选择的目录内，同一类图片、音频或视频至少 300 个，且至少 70% 文件名符合机器命名规则时，排除该目录的这三类媒体。相机前缀及日期命名有豁免；可以通过 `includeDatasets` 改变该过滤。不能将此描述为已准确识别所有训练数据集。[D01] [D26]

### 代码索引

`code.sqlite` 有独立文件集合、关键词结果和语义分布；`code:` 查询选择代码索引，并使用 `task: code retrieval` 提示词。普通查询使用 `task: search result`。代码可用同一模型，不混入普通文件排名。[D20] [D23] [D40]

代码目录只收录指定源码、文档、配置和 Notebook 类型；排除 vendor、构建产物、数据文件、压缩代码、密钥类文件等。Git 仓库调用 `git ls-files -z --cached --others --exclude-standard`，保留已跟踪及未被忽略的新文件；它遵循 Git 返回的集合，已跟踪文件不会因后来写入 `.gitignore` 就自动排除。无 Git 或列举失败时，这一步不提供忽略过滤。遍历到 `.git` 为文件的子目录时排除，但直接选择该目录作为根是另一入口。[D26] [D27]

普通代码文件上限为 1 MiB，Notebook 文件上限为 20 MiB，抽取单元格源码后仍有 1 MiB 上限。Notebook 不读输出。内容检查会排除私钥文本、部分生成标记和压缩源码；这些是具体规则，不能扩展成所有敏感内容均可识别。[D05] [D28]

### 代码切分和符号定位

按完整行切成约 1,800 字符的片段，优先在空行或左侧顶格的块起点附近结束；被迫中断时重叠两行。超长单行最多保留 4,000 字符。标题包含仓库名及相对路径，片段记录起止行；Notebook 用起止单元格号。[D28]

snake_case、camelCase、带数字或限定符等符合规则的查询，会作为标识符短语查找。前十条文件结果额外检查最多 300 个命中片段，用正则、关键词和行内上下文判断定义或声明，优先定义；找不到时定位关键词所在行或片段首行。源码未建立 AST、语言服务器符号表或引用关系索引，故不能宣称完整的“跳转到定义”能力；单词形式的 `retry` 等也未必进入标识符专用分支。[D23] [D29]

## 4. 中文、跨语言和声明的证据边界

### 中文有两项需要单独说明的限制

1. **关键词没有中文专用分词。** 索引 tokenizer 为 `porter unicode61`，并做 Unicode 兼容规范化和部分文字处理；查询词按非字母数字字符切分。连续汉字不会在此流程中按中文词语拆开。缺失的三字符以上整词可尝试前缀匹配，但这不等于任意子串检索或中文分词；单字查询还会被至少两个 Unicode scalar 的条件过滤。[D20] [D24] [D30]
2. **正文向量存在按空白计词的前置条件。** `hasProse` 要求非空白字符中至少约五分之一为字母类，并至少存在四个“由空白分隔且包含字母的单元”。普通文档和文本 PDF 页使用此条件。代码推导：一整段无空格、无换行的中文会被当成一个单元，无法通过这项检查，保留关键词正文但不生成文本向量；有多个换行或空格的中文结果可能不同。图片、扫描页图像向量不受此条件控制，代码片段也只使用较宽松的 `hasWords`。[D08] [D30]

因此，README 对中文等语言的限制只强调关键词未分词，仍声称语义检索适用；该概括没有覆盖上述普通正文可能不生成向量的分支。中文整体效果未实测，不能直接按模型语言数量推断。[D30] [D31]

### 跨语言依据

默认实现直接把查询和内容交给同一嵌入模型，没有独立翻译或中文专用检索路径。项目说明模型支持超过 100 种语言；本次未核验模型本身的多语言测评。公开多语言查询集实际覆盖英语、孟加拉语和阿拉伯语，包括跨语言文档、图片和音频查询，没有中文查询。macOS OCR 使用系统 Vision；Windows/Linux 的 OCR 实现返回空文本，截图和扫描页的精确文字能力不同。[D12] [D17] [D30] [D31] [D32] [D33] [D44]

来源：[D23] [D25] [D34] [D35] [D36] [D43] [D44] [D45] [D46]。公开评测中，脚本报告的 `R@k` 实际统计“前 k 条是否命中任一预期答案”，有位置条件时还检查页码、时间范围或代码片段范围；不统计是否找全全部相关文件。代码片段采用范围重叠判断，并未要求精确命中定义行。因而这些指标不能直接当作完整召回率或精确符号定位准确率。[D35]

## 5. 可借鉴机制

以下仅为 DigUp 已有设计的参考价值，不判断 SAG 是否具备，也不据此提出产品改动：

- 先给每个文件建立可搜索内容，再补长文件剩余部分，并保存逐步进度。[D03] [D08]
- 保存片段位置，将搜索结果定位到页、时间或代码行。[D08] [D23] [D28]
- 明确区分语义排序、关键词覆盖率和按模态调整分数，长文件后续内容不改变统计基准。[D23] [D25]
- 用独立代码索引和不同同步频率控制普通文件与源码的互相影响。[D06] [D20]
- 独立进程释放模型及解码缓存，并按本机实际成本修正预计耗时。[D03] [D09] [D15]
- 记录模型及向量版本，用固定输入的参考向量检查升级兼容性。[D17] [D36]

## SAG 当前实现核对

核对对象：SAG 本地工作区，提交 `f2242427c1d59b13370a33a9d2cba57f510731af`。以下描述以源码为准；本次未运行模型、性能基准或双方同题评测。

### 索引与检索流程

- 原生文本读取后按结构切片，使用 Jieba 分词，写入 SQLite 全文索引；不生成文档 embedding。[分词](../../core/src/text.rs#L66)、[分块与入库准备](../../core/src/store.rs#L1529)
- 快速搜索使用 BM25，对同一文件的片段归组。[快速搜索](../../core/src/store.rs#L1757)
- 深入检索先从全文索引召回候选，再请求 Jev 判断候选对原问题是否提供必要证据；从高分片段提取词项和名称继续检索，结合已有证据再次评分，最后在本地排序和多样性处理。[召回与扩展](../../core/src/retrieval.rs#L231)、[评分请求](../../core/src/models.rs#L207)、[排序](../../core/src/retrieval.rs#L381)
- 默认首次召回后扩展一次；最多扩展两次。桌面深入搜索每轮候选固定为 100，问答默认每轮 50。[默认参数](../../protocol/src/types.rs#L195)、[桌面搜索入口](../../core/src/retrieval.rs#L183)
- 远程 Jev 收到原问题、候选标题和正文，以及该轮使用的已有证据。Jev 地址可配置为本机服务；应用当前通过服务接口调用它。[请求内容](../../core/src/models.rs#L207)
- 图片和扫描件通过 OCR 提取文字；音视频使用本地 Whisper 转写为 Markdown。视频会抽取画面，但当前检索链路未建立画面语义向量。[OCR](../../core/src/docling_runner.py#L39)、[音视频](../../core/src/docling_media_runner.py#L43)
- 已有文件监听、增量更新、内容指纹、忽略规则、暂停、索引状态、原文位置；原生文本先于格式转换处理，并分批提交已完成文件。这些属于现有能力。[监听](../../core/src/indexer.rs#L41)、[指纹](../../core/src/store.rs#L1542)、[忽略规则](../../core/src/ignore_rules.rs#L5)、[处理次序](../../core/src/store.rs#L1112)、[来源位置](../../protocol/src/types.rs#L124)

### 优势与限制

| 项目 | SAG | DigUp |
| --- | --- | --- |
| 原生文本首次索引 | 无向量推理开销；仍需读取、切片、分词 | 需要为内容生成向量 |
| 搜索服务依赖 | 快速搜索本地；深入检索依赖配置的 Jev | 语义与关键词搜索均可本地运行 |
| 无共同关键词的提问 | 初始候选来自词项匹配，存在漏召回风险 | 语义向量提供额外召回能力，实际效果取决于模型 |
| 跨文件证据 | 有扩展检索及结合上下文的证据判断 | 当前主要为相似度与关键词排序，未见同类证据扩展循环 |
| 图片、音视频 | 当前主要搜索 OCR 与转写文字 | 直接索引画面和声音的语义 |
| 中文关键词 | 已有 Jieba 分词 | 缺少中文分词；部分无空白分隔的中文正文还会被前置条件排除而不生成向量 |
| 资源成本 | 文本索引轻；OCR/转写和 Jev 仍有成本 | 增加模型、向量磁盘与搜索内存成本 |

表中相对优缺点属于基于实现的判断，不等于双方实测排名。SAG README 中“百万字约 200 ms”的描述不能直接用于包含 PDF 转换、OCR 或转写的全流程比较；DigUp 的示例耗时也不能直接与之比较。

### 可借鉴方向及优先级

1. **优先验证可选语义召回。** 在选定资料上生成向量，将语义候选与 BM25 候选合并、去重，再交给现有 Jev 评分。目标是补充同义改写、无词面重合、跨语言问题的候选。该变化会增加预处理、存储与模型管理成本，建议以独立实验验证后再决定产品默认行为。
2. **按需求增加画面语义检索。** 图片与视频画面的检索能力可作为独立功能，与已有 OCR/转写文字同时保留；文件、页码、时间点应绑定到同一来源。不能仅凭支持图片和视频文件格式，就认为具备画面语义检索能力。
3. **改善首次处理的可预期性。** 借鉴按本机实测成本估算各类文件耗时，以及长文档分段可用的策略。SAG 已有原生文本优先、分批提交、暂停和进度显示，新增价值主要在于耗时估计和单个长文件内的分阶段处理。
4. **按使用场景改善代码结果。** 可评估独立代码搜索范围、定义位置优先、项目相对路径与函数上下文。SAG 已支持代码文件、忽略规则和行级来源，无需将这些基础能力重复列为新增需求。

不要直接照搬基于空白计词的正文过滤、固定的分数权重、阈值、向量精度或全量内存检索实现。它们与语料规模、模型、中文资料占比和使用场景有关。

### 验证标准

固定同一份资料，分别覆盖：准确名称与编号、中文改写、无共同关键词、跨语言、跨文件关系、图片画面与视频场景。先统一结果单位（文件与证据片段分别统计），再记录前 10 条结果的证据覆盖、错误匹配、首次全流程耗时、增量更新时间、索引大小、内存、查询延迟与 Jev 请求量。确认新增语义路径能改善目标题型，并核对已有准确名称/编号题目有无退步，再决定是否启用。

当前结论：保留 SAG 的文本索引和证据检索优势，优先验证补充召回与多模态能力；尚无同条件实验支持宣称任一方案整体更准确。
