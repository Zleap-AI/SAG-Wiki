# 300 页 PDF：分阶段索引性能与回归

状态：实现、针对性回归及两轮无编译干扰的真实文件对比已完成；未发布安装包。

提交整理说明：本报告的完整 PDF 测量先于 PR 与 GitHub `main`（`9a874f1d8b18d36efb7fc6460402fe2eaa9b3a6f`）整合。整合保留了失败文件重试与分段进度，并补充失败 PDF 重试不阻塞新文件的回归；本轮未重新执行 300 页整文计时。以下性能数据仍对应原固定二进制，不代表整合后提交的重新测量。

## 实现与范围

基于 2026-11-13 拉取的 `origin/main`：`fc5953c8f7420eb916b85c6f9a3a53ae2438d00b`。保留 SQLite FTS5，复用 AnyDoc 已有的 pdf-inspector 1.25.2 逐页位置解析接口，先发布可检索的基础文本，再后台补充 OCR/表格。纯文本 PDF 保持 AnyDoc 快速完成路径。

基础索引与增强使用独立工作线程，数据库、查询缓存、解析组件和准备预算共享；进度、日志和取消按任务通道隔离。同目录和其他目录的新文件都能在 OCR 仍阻塞时建立基础索引。后台批次继续遵守 `conversion_workers`，不把已有并行转换设置退化为串行。

界面区分等待解析、基础文本可搜索、增强中、增强失败及等待 OCR；没有有效正文时不显示为可搜索。增强失败保留仍与原文件一致的基础文本；源文件变化、删除、排除和目录重新添加均有回归覆盖。中英文 folders/models 页面和演示截图同步更新。

## 对比

正式两轮分别在其他构建退出且连续 5 分钟无编译器/链接器活动后运行；中间出现新构建的优化轮被排除，另行重测。两轮使用同一计时与采样脚本，记录开始/结束系统状态，并每秒记录外部编译器数量。本任务期间不再并行构建或测试。前面各轮诊断数据不替代正式对比。

| 指标 | 原版 `before-stable` | 优化版 `after-comparable` |
| --- | --- | --- |
| 首批正文实际命中 | 1,045.775 秒 | 21.549 秒 |
| 整文处理结束 | 1,045.778 秒（17 分 25.8 秒） | 1,064.465 秒（17 分 44.5 秒） |
| 首批覆盖 | 300 页处理后整文发布 | 61 页文本层，第 140–200 页；656 块 |
| 进程树 RSS 峰值 | 3,235,104 KiB（3.085 GiB） | 2,951,424 KiB（2.815 GiB） |
| 完成后文档 / 分块 | 1 / 2,447 | 1 / 2,411 |
| 文本层词与扫描页词检索 | 三词全部命中 | 三词全部命中 |

首次命中等待缩短 97.94%，约提前 17 分钟；这一指标只针对已有文本层的内容。整文完成实测增加 18.687 秒（1.79%），本轮没有体现整文吞吐提升。峰值 RSS 单次观测下降约 8.8%，仍须按下述采样与环境限制理解。

两轮设置 JSON 完全一致、进程退出码均为 0、目录均为 `ready`，优化版最终文件状态为 `complete`。外部编译器每秒采样分别 984 / 1,000 次，均为零。系统平均负载及换页仍有波动：基线开始/结束 swap 已用约 23,025 / 24,520 MiB，优化版约 24,850 / 26,354 MiB；等待构建结束不等于干净重启的实验机。因此 1.79% 的完整耗时差异和 RSS 变化不作统计显著性结论。

**测量边界：** 两轮均以实际 `search_files("defects")` 首次命中计时，100 ms 轮询，并保留首批正文快照。优化版首批只覆盖已提取文本的页面，不是相同覆盖量的整文索引速度比较。最初诊断轮的轮询曾漏掉原版最后提交，原始空值保留；该轮不进入正式对比。

RSS 为每秒一次的本进程及子进程 RSS 求和，共享页可能重复计数，瞬时峰值可能漏采；不是硬性内存上限或内存分配剖析。

## 正确性与瓶颈证据

PDFium 独立检查得到 61 个有文本层的页面、227,549 个字符。优化版正式轮基础快照与这 61 个原始页码完全一致，状态为 `basic`；快照为 229,443 字符（包括 Markdown），656 个分块。`defects` 在基础阶段实际命中；基础快照不包含扫描页词 `Cranford`、`Gaskell`。全文完成后，三词在两版的实际检索中均各命中 1 份文档。两版最终均有六个来源页范围标记，联合覆盖 1–300 页；范围标记不代表逐页 OCR 质量已经人工验收。

正式两轮的分段缓存完成时间近似如下（包含解析路由和模型启动；首段也包含准备过程。按缓存文件时间估算，不是独立 OCR profiler）：

| 页码 | 原版（约） | 优化版（约） |
| --- | --- | --- |
| 1–50 | 274.2 秒 | 286.9 秒 |
| 51–100 | 215.3 秒 | 198.5 秒 |
| 101–150 | 199.2 秒 | 164.0 秒 |
| 151–200（全部有文本层） | 0.17 秒 | 35.4 秒 |
| 201–250 | 162.1 秒 | 178.2 秒 |
| 251–300 | 194.5 秒 | 201.2 秒 |

两版最后一段缓存成功到整文完成都不足 1 秒。这份文件主要受解析/OCR 和整文发布等待影响，现有证据不支持优先更换 FTS 引擎。

混合 PDF 的后台增强会走增强解析路径，其中全有文本层的 151–200 页也进入 Docling 处理，原版这段由 AnyDoc 快速完成。这解释了一个额外成本来源，其他扫描段耗时也存在环境波动；不能把全部差异归因于线程拆分。纯文本 PDF 整文仍保留快速完成策略，不自动启动该增强。

增强 Markdown 的结构与内容选择发生变化：最终字符数从 821,685 变为 808,756，分块从 2,447 变为 2,411。三词回归和页范围覆盖已通过，不能据此宣称逐字内容、OCR 与复杂表格准确率等价；后续模型或按页路由优化应补充专门质量样本。

该文件页面指令合计解码约 633 MiB，单页最大约 4.68 MiB；字体、Form、元数据等其他非图片资源约 1.6 MiB。累计处理的页面指令量不是同时驻留的正文内存：预检保留单流/单页解码上限，常驻资源使用准备预算，输出正文另行限额。不能把所有页的绘图指令累计计为“解码正文”，否则会错误拒绝本文件。

## Gety 技术参考（2026-11-13 官方资料复核）

Gety 官方明确把索引分成快速索引和正文提取，并显示“基础提取完成、OCR 进行中”：已有正文可以搜索，扫描内容继续处理。这是本次分阶段发布及明确状态最直接的参考；文件名可找到并不等于全文提取完成。[官方故障排查](https://docs.gety.ai/troubleshooting)

其产品页的 0.01 秒描述的是搜索结果响应，不是导入大扫描 PDF 的 OCR 时间；不能据此推断同一文件整文索引只需毫秒。本任务没有在 Gety 上运行该文件，也没有同机同覆盖量的竞品数字。[Gety 与 Listary](https://gety.ai/gety-for-listary/)

官方更新记录还披露自研 OCR、NVIDIA GPU/Intel NPU 加速、按系统负载及电源自动调速、全速/暂停模式，以及空闲后释放 GPU 内存。它也明确提醒大型资料库首次索引可能持续数小时。这些是后续可评估方向，官方倍率不能移用为 SAG Wiki 的预期收益。[官方更新记录](https://gety.ai/changelog/)

本次查阅的官方资料未披露其倒排索引库、PDF 解析器、OCR 模型或调度实现，不能把它推断成 Tantivy、SQLite 或某个具体 OCR 框架。当前证据支持先拆开可用性与增强成本；若继续降低整文耗时，下一步应测量按页跳过无需 OCR 的内容、模型常驻与进程启动开销，并以扫描页识别及表格质量评估约束加速方案。硬件后端或模型替换需要另外确定平台、包体和质量取舍，本次没有擅自切换。

## 排除的试验

- 运行环境首次未提供 QPDF、组件外部符号链接被校验拒绝：补齐运行条件后重测，不计入结果。
- 原始 lopdf 字符串提取把位置间距丢失，出现 `clusterdefects`，尽管很快发布却无法命中 `defects`：已拒绝，改用现有位置解析接口，并补回归。
- 将累计绘图/字体资源误计为正文预算的候选：真实文件回归拒绝，已修正预算维度，没有调大默认参数。
- 构建/检查与长跑重叠的诊断轮出现持续换页，完整计时作废。`after-stable` 虽在连续 5 分钟无编译器后启动，但运行约 853 秒后外部构建再次出现；该轮后半程与完整计时作废，停止本任务的测量进程，其他项目不受操作影响。其 22.105 秒基础快照仅作正确性证据；之后的 `after-quiet-final` 同样因新构建重启而中止；首批 21.711 秒已记录，但该轮也不作正式完整对比。最终使用全新目录 `after-comparable` 重测并完整结束，只有该轮进入正式对比。

## 复现与产物

```sh
cargo build --release --manifest-path core/Cargo.toml --examples
export SAG_BENCH_DOCLING='/path/to/installed/docling'
export SAG_QPDF='/path/to/qpdf/bin/qpdf'
python3 scripts/measure-index.py core/target/release/examples/index_baseline /path/to/300_1.pdf /fresh/output
```

`SAG_BENCH_BASIC_ONLY=1` 可单独检查基础提取，不能把这个耗时当整文完成耗时。`index_probe` 示例用于查询回归；`index_baseline` 保存首个查询命中时的正文和状态快照。

基线导出原提交后，只加入同一测试示例；基线没有 `scan_basic` 诊断接口，该未使用的分支适配为 `scan`。正式两轮均不设置 `SAG_BENCH_BASIC_ONLY`，都执行完整 `Store::scan`。

正式数据目录为 `qa/progressive-index/before-stable/` 与 `qa/progressive-index/after-comparable/`。`basic-coverage.json`、`part-timings.json`、`probe.json` 及上级 `comparison-checks.json` 保存核对结果；固定二进制的 SHA-256 记录在 `fair-binaries.sha256`。

原始 `result.json`、`measurement.json`、`run.log`、`first-search/` 和查询检查均位于本地 `qa/progressive-index/`，该目录已忽略，不提交 PDF、提取正文或本地产物。可提交的脚本、报告、中英文文档、截图及 Rust 锁文件均随源码维护。未发布安装包。
