# 后台 OCR / 表格增强：阶段诊断与后续优化方案

后续已按用户选择实施同一 PDF 的模型复用，结果见 [实施与真实文件对比](2026-11-13-pdf-session-reuse-performance.md)。

2026-11-13。本轮完成实际阶段计时和参数对照，未修改生产解析流程、默认线程数或识别模型。

用户决定：保持当前 CPU 使用策略，优先减少重复启动开销。此前分阶段索引的完整 300 页正式结果见 [上一轮报告](2026-11-13-progressive-index-performance.md)：优化版整文完成 1,064.465 秒。本文的样本计时不能替代该完整结果。

## 条件与反馈环

复用上一轮相同的本机、Docling 2.140.0 文档组件、PP-OCRv6 small ONNX 模型、默认 2 个推理线程，OCR/表格全部开启，云解析关闭。没有安装或更换依赖。

从用户提供的 `300_1.pdf` 用 QPDF 提取两个样本，原始页码保留在试验记录中：

- A：1、25、100、140、150、175、185、225 页，共 8 页，兼有扫描页和文本页。
- B：181、182、185、187、190、191、192 页，共 7 页；实际识别出 3 个表格。

本地诊断脚本开启 Docling 自带的 `profile_pipeline_timings`，包装 `DocumentConverter.convert` 和 `RapidOCR.__call__`，记录冷/热运行、OCR 检测/方向分类/文字识别子耗时、Markdown 哈希和表格数。包装器及完整原始结果位于被忽略的 `qa/ocr-stage-profile/`；不提交 PDF 或提取正文。`summary.json` 汇总各组结果。

反馈环直接运行当前 `core/src/docling_runner.py` 和已安装组件，未通过 mock 模型推断性能。单组约几十秒，适合逐项排除假设；本轮不是应用端到端 300 页计时。

## 假设与结果

| 假设 | 实际证据 | 判断 |
| --- | --- | --- |
| PDF 解析或入库占主要时间 | A 热运行解析约 0.11 秒；上一轮最后分段完成到整文发布不足 1 秒 | 当前优先级低 |
| OCR 是主要计算瓶颈 | A 热运行 16.67 秒，管线 16.49 秒，OCR 阶段累计 15.95 秒 | 支持 |
| 表格识别可以解释十几分钟 | B 热运行 3.46 秒；OCR 2.90 秒、表格 2.15 秒，阶段相互重叠 | 样本不支持把关闭表格作为主要解法 |
| 分段重复启动有可省成本 | 当前 Rust 对每个 PDF 分段启动新进程；Python 每次导入库并创建转换器。复用时省去重复导入和首次初始化 | 支持，可在相同线程下优化 |
| 盲目增大批量即可提速 | OCR 内部识别批量 6 → 16 后样本更慢，且文本改变 | 排除该候选 |

计时会重叠，不能把各阶段秒数直接相加，也不能把阶段累计耗时当作独占 CPU 百分比。

A 的一次默认热运行，RapidOCR 子阶段累计为：

| 子阶段 | 秒 |
| --- | ---: |
| 文字区域检测 | 4.88 |
| 方向分类 | 0.14 |
| 文字识别 | 10.52 |

文字识别网络是首要计算成本。页面图像准备及其余 OCR 处理在该样本中不是主要部分。A 的 17 次 OCR 调用对应 17 个不同输入图像哈希，样本没有证明简单的相同裁剪图缓存能带来收益。

## 对照试验

所有“热运行”均为同一转换器第二次转换；冷运行转换耗时另列，进程导入时间不计入该列。

| 配置 | A 冷转换（秒） | A 热转换（秒） | 输出 |
| --- | ---: | ---: | --- |
| 默认 2 线程 | 21.99 / 19.56 | 16.67 / 16.37 | 两次对照均一致 |
| 4 线程 | 15.46 / 15.31 | 13.41 / 14.74 | 与默认 Markdown 哈希一致 |
| 8 线程 | 16.05 | 12.85 | 与默认 Markdown 哈希一致 |
| 4 线程、识别批量 16 | 16.99 | 14.64 | 与默认 Markdown 哈希不同 |

4 线程在两次对照中的热运行改善约 10%–20%；8 线程的进一步收益较小，且没有足够重复次数作精确倍率结论。一次资源采样中，2 / 4 线程进程 CPU 峰值约 248% / 384%，与增加 CPU 使用量一致；管线还有辅助工作，推理线程数不等于整进程严格 CPU 核数上限。按照用户决定，不调整当前线程默认值，不把这条路线列入拟实施方案。

识别批量指 RapidOCR 的 `Rec.rec_batch_num`，与应用现有的 `ocr_batch_size` 不同：当前 Docling RapidOCR 实现仍逐页、逐裁剪调用识别器。仅增大管线收集批量不能直接把这些调用变成一次跨页神经网络推理。批量 16 这一组比对应 4 线程基准热运行慢约 9%，不采用；没有判断变化后的文本更好或更差。

B 的 2 / 4 线程热运行分别为 3.46 / 3.11 秒，都识别出 3 个表格，Markdown 哈希一致。表格阶段确有成本，但不应为节省少量时间直接取消已承诺的表格能力。

## 相同 CPU 下的复用可行性

一个转换器按 A → B → A 连续处理：

| 输入 | 转换耗时 | 表格数 | 结果核对 |
| --- | ---: | ---: | --- |
| A，首次 | 23.60 秒 | 0 | 与独立 A 哈希一致 |
| B，复用模型 | 4.58 秒 | 3 | 与独立 B 哈希一致 |
| A，再次复用 | 18.23 秒 | 0 | 与首次 A 哈希一致 |

该进程库导入另耗时约 5.54 秒（以原始 JSON 为准）。默认 A/B 试验的库导入约 3–7 秒，首次转换还多出数秒初始化/预热。因此 300 页按 6 个分段处理时，避免后 5 次重复启动的预期收益是几十秒量级；约半分钟至一分钟只能作为待验证估算，不能冒充新的整文实测结果。首次与复用差异也包含运行时预热和负载变化，尚未单独剖析各模型加载耗时。

这组试验证明转换器可跨这些输入复用，没有观察到文档结果串用；它不等于生产 Worker 的取消、进程崩溃、资源释放和全量质量验证已完成。

## 建议的具体实现

优先采用“同一 PDF 内共享转换器，整文结束即释放”的短生命周期会话：

1. 本地 PDF 分段第一次进入 Docling 时启动一个受监督进程，导入模型并建立转换器。
2. 后续分段通过有请求编号的管道提交，串行使用同一个转换器；仍为当前 2 个推理线程，不增加 PDF 分段并发。
3. 保留每 50 页的输出校验、原子发布、成功分段缓存和原始页码映射；不把 300 页合成一个不可恢复的大任务。
4. 会话沿用现有转换内存许可和每段超时，进程存活期间计入预算；取消、超时、超内存和崩溃必须终止进程并释放许可。
5. 失败分段按现有后端兼容规则回退；失败的 Worker 不继续复用。完成、失败或停止整份 PDF 后立即释放，不额外保留跨文档常驻内存。
6. OCR 模型、图像分辨率、识别批量、表格选项和普通文档路由保持原样。云解析流程保持原样。

选择原因：这条路线直接消除已确认的重复开销，同时符合当前资源偏好。跨文档保留 Worker 可以继续减少小文件启动成本，但会延长模型和内存许可驻留，暂不作为默认方案。取消分段、直接一次处理 300 页则会削弱检查点恢复和资源隔离，也不采用。

落地前的回归重点：连续不同分段的隔离、一个 PDF 只初始化一次、完成/取消后无存活子进程或许可泄漏、失败不发布部分输出、后端兼容回退、内存限制、多文件调度，以及该 300 页文件的完整同条件前后对比。现有阶段诊断不替代这些生产验证。

## 后续更大幅度提速的边界

相同 CPU、相同模型且需要完整 OCR 时，主要的文字识别计算仍要执行。若希望把十几分钟进一步明显压低，需要另行评估 OCR 推理后端/硬件加速或模型选型，并补充中文、英文、扫描件与表格质量回归；不能只针对本文件的英文内容换更小的英文模型。当前未做这些技术切换。

参考官方 [管线选项](https://docling-project.github.io/docling/reference/pipeline_options/) 与本地组件的 `docling/utils/profiling.py`、`models/stages/ocr/rapid_ocr_model.py`。具体阶段与默认行为以本地已安装 2.140.0 源码及本轮实测为准。
