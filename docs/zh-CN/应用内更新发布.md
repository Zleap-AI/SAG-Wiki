# 应用内更新发布

[English](../en/app-update-publishing.md) · [文档目录](README.md)

正式桌面版本统一通过 GitHub Actions 的受保护环境签名。开发者在本机构建、测试时无需持有发布私钥。客户端内置公钥，下载更新后校验签名和签名绑定的版本，再显示“重启并更新”。更新签名与 Apple 公证、Windows 代码签名分别配置。

## 一次性配置签名环境

首次签名发布前，仓库管理员必须配置 `release` Environment：

- 仅允许匹配 `v*` 的版本 tag 部署；工作流还会校验精确的 `vX.Y.Z` 格式，以及 tag 指向的提交属于 `main`。
- 设置发布审核人，并禁止发起部署的人自行批准。
- 将 `TAURI_SIGNING_PRIVATE_KEY`、`TAURI_SIGNING_PRIVATE_KEY_PASSWORD` 保存为 **Environment secrets**。工作流 YAML 只引用 Secret，私钥和密码不能进入 Git、日志、制品或安装包。
- 按组织权限制度保留一份独立、加密的私钥及密码恢复备份。GitHub Secrets 用于发布时读取，不能作为唯一恢复副本。

没有既有发布密钥时，在受控的管理员会话中生成一次密钥对：

```sh
node scripts/generate-updater-key.mjs --output /secure/signing-recovery
```

脚本拒绝仓库内路径和已存在的输出目录，生成加密的 `updater.key`、独立的 `updater.password` 和公钥文件；密码不会进入进程参数或命令历史。目录权限为 `700`，文件权限为 `600`。将恢复材料转入组织批准的密码管理器，只将配套公钥提交到 `src-tauri/tauri.conf.json`。后续版本持续使用同一密钥对，无需每次发版重新生成。

将私钥及密码准备为权限受限的本地文件后，执行：

```sh
node scripts/configure-release.mjs \
  --key-file /secure/updater.key \
  --password-file /secure/updater.password \
  --reviewer luoshuai990529
```

该管理员操作配置环境保护规则，并从文件上传 Secret，不打印密钥内容。仓库 Maintain 角色不足以配置受保护环境；如果 GitHub 返回 403，需要管理员完成这一步。本机构建成功不代表签名环境已经配置完成。

管理员还应在 **Settings → Environments → release** 中取消 **Allow administrators to bypass configured protection rules**。GitHub 公共 REST API 未暴露此开关，须在界面人工核对；下面的自动检查覆盖审核人、禁止自行审核和 tag 限制。

发布任务会在签名前检查环境保护，也可单独检查：

```sh
node scripts/release.mjs verify-environment
```

当前采用单维护者策略：`luoshuai990529` 发起发布请求，再手动批准由自动账号启动的签名任务。保留“禁止自行审核”，部署发起人是自动账号。这是一次人工确认，不属于两人独立复核。如需双人审核，应配置另一位实际可联系的维护者。

## Apple 凭据：由管理员直接配置

由凭据负责人和仓库管理员直接在 **Zleap-AI/SAG-Wiki → Settings → Environments → release → Environment secrets → Add Secret** 配置 Apple 凭据。使用已获准用于 Wiki 的公司发布身份，优先采用为 Wiki 独立管理、轮换的凭据。签名流程不从其他仓库读取或转交凭据。

1. 凭据负责人准备有效的 **Developer ID Application** 签名身份，导出为有密码保护、同时包含证书和私钥的 `.p12`。只有 `.cer` 公钥证书不能签名。应从公司批准的凭据库或原签名电脑恢复完整身份；若无法恢复，由 Apple 账号负责人安排新的签名身份。参见 [Apple 证书导出说明](https://developer.apple.com/documentation/Xcode/sharing-your-teams-signing-certificates)。
2. 准备证书的 Base64 文本、导出密码、具有对应开发者团队权限的 Apple 账号和该团队 ID。在 **account.apple.com → 登录与安全 → App 专用密码** 中为 Wiki 单独生成并命名 App 专用密码，不使用 Apple 账号登录密码。参见 [Apple App 专用密码说明](https://support.apple.com/en-us/102654)。
3. Wiki 仓库管理员在现有 `release` 环境添加以下五个 **Environment secrets**：

| Secret | 内容 |
| --- | --- |
| `APPLE_CERTIFICATE_BASE64` | 包含私钥的 Developer ID Application `.p12` 的 Base64。 |
| `APPLE_CERTIFICATE_PASSWORD` | 该 `.p12` 的导出密码。 |
| `APPLE_ID` | 公证所用 Apple 账号邮箱。 |
| `APPLE_APP_SPECIFIC_PASSWORD` | 为 Wiki 生成的 App 专用密码。 |
| `APPLE_TEAM_ID` | 与证书和账号权限对应的 Apple 开发者团队 ID。 |

保留原有两个 `TAURI_SIGNING_*` Secret，以及环境审核人、禁止自行审核、管理员不可绕过和仅限 `v*` tag 的保护规则。添加凭据时不要重建环境。私密值由获准的管理员直接填写到 GitHub 的 Secret 设置，不进入源码、聊天、工单、制品或日志；在公司批准的凭据库保留独立恢复副本。macOS 签名任务使用临时钥匙串导入身份，并在结束时清理。

配置完成后，只需告知五项名称已配置。真实签名、公证和最终包验收等待凭据就绪、修复后的流水线可用后再执行。添加 Secret 或重跑旧流水线不会给既有安装包补上公证。配置凭据不等于批准版本变更、tag 或 Release；两个平台实际正式签名验收全部通过、且用户明确批准发布操作前，发布保持阻断。

## Windows 正式签名仍待接入

Windows 签名提供方和资源仍在核实，本次没有建立可用的签名服务。受保护的 `windows-verify` 任务**只做验证，不签署文件**；在获准的签名提供方接入前，它会按设计拒绝当前未签名构建并阻止新版本发布。

NSIS 安装包、已安装桌面程序、包内 CLI 和 NSIS 卸载程序，均须具有有效的**嵌入式 Authenticode 签名**、与 `WINDOWS_SIGNING_PUBLISHER` 一致的获准发布者，以及可信时间戳。发布组装还要求来自本次成功的受保护 Windows 验证任务、绑定安装包字节和源码的证明。更新签名不能代替这些检查。只有 macOS 实际签名、公证和 Windows 实际正式签名验证全部通过，下一版本才具备发布条件。

## 构建与发布流程

1. 创建版本 PR 或修改版本号前，先取得用户单独批准，再按获准范围更新桌面端和 CLI 版本、lock 文件及 Changelog。代码审查和无需密钥的 CI 检查通过后，合并到 `main`。本次签名基础设施变更不包含版本变更或版本 PR。
2. PR、推送 `main` 和手动触发的 **Desktop build and release** 均执行完整的 macOS、Windows 桌面构建及测试，包括发布校验、文档构建、前端与原生测试、桌面打包、macOS 包内 CLI 检查，以及 Windows 安装冒烟与已安装 CLI 的 Jev E2E。原有 **PR E2E** 继续在两个平台编译 CLI 并运行轻量协议回归。普通构建继续使用 macOS ad-hoc 签名，Windows 仍为未签名，不读取发布 Secret，完整回归范围不变；这些检查仍不能替代代表性用户环境中的升级和数据保留验收。
3. 签名资源接通、且用户明确批准 tag 与发布操作后，在已验收的 `main` 提交上创建 `vX.Y.Z`，再从 `main` 运行 **Request desktop release** 并填写该 tag。仅推送 tag 不会启动签名。发布请求使用 `github-actions[bot]` 身份启动 tag 工作流，不创建或移动 tag；工作流拒绝版本不一致或不属于 `main` 的 tag。
4. 两个平台的构建均通过后，tag 发布进入受 `release` 环境保护的 `macos-sign` 和 `windows-verify` 任务，等待审核人批准。Windows 任务验证上述四个程序及安装验收，不提供签名服务。macOS 任务下载并核验已测试制品，不重新编译；先单独给包内 CLI 加上 Developer ID、hardened runtime 和可信时间戳签名，再签署外层应用。应用完成公证并装订票据后，重新生成、签署、公证和装订 DMG。签名检查、Gatekeeper 检查、DMG 与更新包内容一致性检查，以及最终包内 CLI 验收全部通过后，才上传新的已签名 macOS 制品。
5. 随后的受保护 `release` 任务要求两个任务均成功，重新核验原始来源，仅接受本次成功的 `macos-sign` 任务产出的最终 macOS 压缩包，并要求本次受保护 Windows 验证任务的签名证明。核验制品摘要、来源关系、提交和版本后，才为获准的包生成更新签名、校验和及清单。原始未签名 Windows 安装包不能绕过证明进入发布；更新签名不能代替 Apple 公证或 Authenticode。
6. 工作流创建包含安装包、已签名更新包、清单和构建来源证明的 **GitHub Release 草稿**，不会自动发布仅构建完成一部分的版本。

所有 Action 固定到完整提交 SHA；checkout 不保留凭据。构建任务只读仓库，签名、发布和构建来源证明所需权限仅分配给对应任务。npm 和 Cargo 依赖使用已提交的 lock 文件。已正式发布的制品不能覆盖修补；应修改源码后发布更高版本。

历史安装包抽样核验确认：**0.1.5、0.1.6 已经过 Apple 公证，Gatekeeper 接受；0.1.9 则是 ad-hoc 签名，没有公证票据，Gatekeeper 拒绝。** 不能笼统称所有早期版本均未公证。当前公开发布的 0.2.4 安装包保持不变，包括尚无 Apple 公证和 Windows 正式签名的状态。这些历史制品不代表可以继续发布未签名版本。Apple 凭据配置及真实签名、公证验证仍待完成，Windows 签名提供方仍待接入；两个平台实际检查全部通过前，新版本保持阻断。

仅在上述版本、tag 和发布操作分别获准、签名资源具备条件后，才在已审查且干净的 `main` checkout 中执行：

```sh
git fetch origin main --tags
node scripts/release.mjs validate
release_commit=$(git rev-parse origin/main)
test "$(git rev-parse HEAD)" = "$release_commit" || exit 1
release_version=$(node -p "require('./package.json').version")
release_tag="v${release_version}"
git tag -a "$release_tag" "$release_commit" -m "SAG Wiki $release_version"
git push origin "refs/tags/$release_tag"
gh workflow run request-release.yml --repo Zleap-AI/SAG-Wiki --ref main -f tag="$release_tag"
```

如果 tag 已存在，保持原样，只执行发布请求命令。批准前核对发布任务的发起人为 `github-actions[bot]`。

macOS 的 `.dmg` 用于手动安装，`.app.tar.gz` 用作应用内更新包；Windows 的 NSIS `.exe` 同时用于手动安装和应用内更新。集中签名任务生成 `.sig`，并在受签名保护的注释中绑定发布版本。`requireSignedVersion` 始终开启。

## 复用构建与编译缓存

标签发布优先查找同一仓库、同一工作流、同一提交在 `main` 上成功的 push 构建。版本校验、文档、macOS 和 Windows 各任务最近一次执行必须全部通过，且两个平台的制品仍可用。命中后跳过重复的原始构建和测试；未命中则执行完整构建。查询 API 失败也会回退到完整构建；普通 main 构建不查询复用 API。`main` 缓存保存普通的 macOS ad-hoc 和 Windows 未签名构建。复用不能满足发布门槛：无论是否命中缓存，tag 发布都必须完成新的 `macos-sign` 最终签名、公证和验收，以及签名提供方接入后的受保护 `windows-verify` 检查。

签名前再次核验来源运行和任务结果，按制品 ID 下载压缩包，验证 GitHub SHA256 摘要，再检查包内记录的提交、版本、平台和各文件摘要。签名后的 macOS 制品与原始缓存分开保存，记录原始文件摘要和 Apple 签名信息；集中发布任务核验其来自本次成功的签名任务，要求本次受保护 Windows 验证证明，并在更新签名前重新核验文件摘要及来源关系。选定后制品过期或丢失会停止发布，可重新运行工作流重新选择或构建。`release` 环境审核和签名版本校验继续执行。

Rust 缓存按 runner 系统/架构、目标平台、Rust 版本、manifest、锁文件及工作流内容隔离，仅可信 `main` push 构建写入。原生测试后保存 debug 缓存并清理 debug 输出，再恢复 release 输出以控制磁盘占用。编译缓存命中仍会执行测试；签名任务不恢复编译缓存，也不缓存密钥。

## 审核并发布草稿

正式发布前，先取得用户明确批准，并确认两个平台的完整构建与回归、Windows NSIS 安装冒烟检查、包内 CLI E2E 均通过。Windows 安装包、桌面程序、CLI 和 NSIS 卸载程序还必须通过嵌入式 Authenticode、获准发布者和可信时间戳检查，并具备本次受保护验证任务的证明。macOS 还必须通过最终应用及 CLI 的 Developer ID/hardened runtime/时间戳检查、应用与 DMG 的公证和票据校验、Gatekeeper 检查、挂载 DMG 与解压更新包的内容一致性及实际包内 CLI 验收。确认 Release 包含两个平台的更新条目与签名。下载草稿制品，核对 SHA256 校验和及构建来源证明。对已下载的制品可执行：

```sh
gh attestation verify /path/to/downloaded-installer -R Zleap-AI/SAG-Wiki
```

校验和用于确认文件字节一致；来源证明用于确认构建源码和工作流，两者均不能替代更新验签或实际安装检查。托管运行器的冒烟检查不代表所有客户机器均已验收。

有权限的发布审核人检查制品及发布说明后，沿用创建阶段已审核的 `release_tag`。若使用新 Shell，先明确设置为本次审核的标签，不要从可能已经切换版本的工作区重新推导：

```sh
: "${release_tag:?Set release_tag to the reviewed release tag before publishing}"
gh release view "$release_tag" --repo Zleap-AI/SAG-Wiki
gh release edit "$release_tag" --repo Zleap-AI/SAG-Wiki --draft=false --latest
```

正式发布后复核公共安装包链接和更新清单。README 指向最新正式版，下载安装页打开时读取该版本的下载地址和附件实际大小，无需再修改版本配置或提交下载文档 PR。

## 0.1.9 密钥迁移

由于此前的私钥不可用，0.1.9 启用新的更新签名密钥。**0.1.8 及信任旧公钥的更早版本用户，需要手动下载安装一次 0.1.9。** 旧公钥无法验证新私钥签署的更新包；完成这次手动安装后，后续使用新密钥签名的版本即可继续通过应用内更新安装。

| 清单 | 对应客户端 | 行为 |
| --- | --- | --- |
| `latest-v2.json` | 内置新公钥的 0.1.9 及后续版本 | 提供当前版本和新签名。 |
| `latest.json` | 内置旧公钥的客户端 | 逐字保留 0.1.8 原清单、旧下载地址与签名。0.1.8 会显示没有更新；兼容的更早版本仍可能升级到 0.1.8。 |

每次成为最新版本的 Release 均保留旧 `latest.json`，避免旧客户端遇到清单缺失或不可信更新。不能把旧清单版本号改成 0.1.9、替换旧签名或关闭验签。发布说明必须明确旧用户需手动升级一次；保留的旧清单不会通知用户存在 0.1.9。

已有 GitHub 仓库配置无需修改，新二进制会为所配置仓库选择 `latest-v2.json`。自定义 **官网** 更新源仍使用用户填写的完整 URL，不会自动迁移。运营方需使用独立地址提供新清单，并为已迁移客户端更新该设置；需要兼容旧客户端时，同时保留旧通道。

## 失败处理与验证边界

- 缺少签名资源或 Secret、环境保护不足、来源提交混用、平台包缺失、Apple 签名/公证/票据/Gatekeeper 检查失败、最终 macOS 包与来源不符、Windows 任一嵌入式签名/发布者/时间戳无效或缺失、缺少本次 Windows 验证证明、更新签名损坏或版本不一致，均须阻止创建 Release，不能回退到未签名的平台构建或更新包。
- 有效的新版本清单可能先触发新版通知；客户端仍会在下载、验签阶段拒绝不可信更新包，并保留已安装版本。
- 前端测试覆盖更新进度、失败重试、未保存文档保护和重复点击；原生测试通过本机 HTTP 服务下载已签名夹具，拒绝损坏内容，仅替换临时应用文件。
- Jev E2E 使用真实服务、CLI、配置持久化、索引和检索流程，远端模型由回环地址的协议夹具提供。它验证集成逻辑，不代表真实 Jev 推理质量或远端部署可用性。
- 关闭设置页不会中断更新下载；退出整个应用后，需要重新下载。更新替换程序文件，不主动清除知识库、会话或本地原文件。仍应保留正常用户数据备份，并在正式发布前验证有代表性的升级安装场景。
