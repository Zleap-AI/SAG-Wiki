# 应用内更新发布

[English](../en/app-update-publishing.md) · [文档目录](README.md)

正式桌面版本统一通过 GitHub Actions 的受保护环境签名。开发者在本机构建、测试时无需持有发布私钥。客户端内置公钥，下载更新后校验签名和签名绑定的版本，再显示“重启并更新”。更新签名与 Apple 公证、Windows 代码签名分别配置。

## 一次性配置签名环境

首次签名发布前，仓库管理员必须配置 `release` Environment：

- 仅允许匹配 `v*` 的版本 tag 部署；工作流还会校验精确的 `vX.Y.Z` 格式，以及 tag 指向的提交属于 `main`。
- 设置发布审核人，并禁止发起部署的人自行批准。
- 将 `TAURI_SIGNING_PRIVATE_KEY`、`TAURI_SIGNING_PRIVATE_KEY_PASSWORD` 保存为 **Environment secrets**。工作流 YAML 只引用 Secret，私钥和密码不能进入 Git、日志、制品或安装包。
- 按组织权限制度保留一份独立、加密的私钥及密码恢复备份。GitHub Secrets 用于发布时读取，不能作为唯一恢复副本。

没有既有发布密钥时，在受控的管理员会话中生成一次密钥对：

```sh
node scripts/generate-updater-key.mjs --output /secure/signing-recovery
```

脚本拒绝仓库内路径和已存在的输出目录，生成加密的 `updater.key`、独立的 `updater.password` 和公钥文件；密码不会进入进程参数或命令历史。目录权限为 `700`，文件权限为 `600`。将恢复材料转入组织批准的密码管理器，只将配套公钥提交到 `src-tauri/tauri.conf.json`。后续版本持续使用同一密钥对，无需每次发版重新生成。

将私钥及密码准备为权限受限的本地文件后，执行：

```sh
node scripts/configure-release.mjs \
  --key-file /secure/updater.key \
  --password-file /secure/updater.password \
  --reviewer luoshuai990529
```

该管理员操作配置环境保护规则，并从文件上传 Secret，不打印密钥内容。仓库 Maintain 角色不足以配置受保护环境；如果 GitHub 返回 403，需要管理员完成这一步。本机构建成功不代表签名环境已经配置完成。

管理员还应在 **Settings → Environments → release** 中取消 **Allow administrators to bypass configured protection rules**。GitHub 公共 REST API 未暴露此开关，须在界面人工核对；下面的自动检查覆盖审核人、禁止自行审核和 tag 限制。

发布任务会在签名前检查环境保护，也可单独检查：

```sh
node scripts/release.mjs verify-environment
```

当前采用单维护者策略：`luoshuai990529` 发起发布请求，再手动批准由自动账号启动的签名任务。保留“禁止自行审核”，部署发起人是自动账号。这是一次人工确认，不属于两人独立复核。如需双人审核，应配置另一位实际可联系的维护者。

## 手动配置 Apple 签名与公证 Secret

选择在 Wiki 自身工作流中直接签名时，Apple 凭据在 **Zleap-AI/SAG-Wiki → Settings → Environments → release** 中配置，与更新签名使用同一个受保护环境。SAG 仓库 `desktop-release` 环境中的 Secret 不会自动提供给 Wiki；GitHub 也不允许取回已经保存的 Secret 原值。不要更改既有审核人、禁止自行审核、管理员不可绕过和仅限 `v*` tag 的规则。

先核实旧签名环境及发布身份。已核验的 Wiki 0.1.5、0.1.6 使用 `SONIER PTE. LTD.`、Team ID `2M9T9QTT55`；签名成功并不表示凭据保存在当前维护者本机。旧执行环境尚未定位时，应先追查或评估复用既有受保护签名服务，不能把导出本机证书作为唯一前提。SAG 的工作流可作为实现参考，但须确认其凭据对应的发布团队，避免未经确认更换 Wiki 的签名身份。以下步骤适用于已确认由管理员向 Wiki 环境提供凭据的方案。

1. 准备 **Developer ID Application** 证书的 `.p12` 备份，文件必须同时包含证书和私钥。只有 `.cer` 公钥证书不能完成签名。没有原始 `.p12` 时，在原 Mac 的“钥匙串访问”中打开“登录 → 我的证书”，找到 Developer ID Application 条目并确认其下有私钥，然后导出为 `.p12`，设置并安全保存导出密码。不要使用 Apple Development 或 App Store 分发证书替代。
2. 在该 Mac 的终端中，将 `.p12` 转为单行 Base64 并直接复制到剪贴板。将示例路径替换为自己的证书路径；此命令不把证书内容打印到终端：

   ```sh
   openssl base64 -A -in /secure/DeveloperID-Application.p12 | pbcopy
   ```

3. 在 Wiki 的 `release` 环境中选择 **Add environment secret**，名称填写 `APPLE_CERTIFICATE_BASE64`，值粘贴上一步的剪贴板内容并保存。然后清空剪贴板：

   ```sh
   printf '' | pbcopy
   ```

4. 新增 `APPLE_CERTIFICATE_PASSWORD`，值为该 `.p12` 的导出密码。如果密码已经遗失，需要在持有私钥的原 Mac 重新导出；不能从 GitHub Secret 恢复。
5. 新增 `APPLE_ID`，值为有权为该开发者团队提交公证的 Apple 账号邮箱。
6. 登录 [account.apple.com](https://account.apple.com/)，进入“登录与安全 → App 专用密码”，为 Wiki 发布生成一个专用密码，将其保存为 `APPLE_APP_SPECIFIC_PASSWORD`。这里使用新生成的 App 专用密码，不要填写 Apple 账号的日常登录密码。
7. 在 [Apple Developer 账号的 Membership details](https://developer.apple.com/account/#/membership) 中确认 Team ID，将其保存为 `APPLE_TEAM_ID`。该团队必须与 Developer ID Application 证书的团队一致。

最终应有以下五个 Apple Environment secrets，命名与 SAG 的发布流程一致；原有两个 `TAURI_SIGNING_*` Secret 继续保留：

| Secret | 内容 |
| --- | --- |
| `APPLE_CERTIFICATE_BASE64` | 包含私钥的 `.p12` 的单行 Base64。 |
| `APPLE_CERTIFICATE_PASSWORD` | 该 `.p12` 的导出密码。 |
| `APPLE_ID` | 公证所用 Apple 账号邮箱。 |
| `APPLE_APP_SPECIFIC_PASSWORD` | 为公证生成的 App 专用密码。 |
| `APPLE_TEAM_ID` | 与签名证书一致的 Apple 开发者团队 ID。 |

只在 GitHub Secret 输入框和组织批准的凭据保管工具中处理这些值，不要粘贴到聊天、工单、源码或日志。工作流在临时钥匙串中导入证书，使用本次任务生成的钥匙串密码，并在结束时清理。配置 Secret 不会自动重新签署既有安装包；首次新版本发布仍需通过环境审核及实际签名、公证和安装验收。

## 构建与发布流程

1. 通过 PR 更新桌面端和 CLI 版本、lock 文件及 Changelog。代码审查和无需密钥的 CI 检查通过后，先合并到 `main`。
2. PR、推送 `main` 和手动触发的 **Desktop build and release** 均执行完整的 macOS、Windows 桌面构建及测试，包括发布校验、文档构建、前端与原生测试、桌面打包、macOS 包内 CLI 检查，以及 Windows 安装冒烟与已安装 CLI 的 Jev E2E。原有 **PR E2E** 继续在两个平台编译 CLI 并运行轻量协议回归。普通构建使用 macOS ad-hoc 签名，不读取发布 Secret；这些检查仍不能替代代表性用户环境中的升级和数据保留验收。
3. 在已验收的 `main` 提交上创建 `vX.Y.Z`，再从 `main` 运行 **Request desktop release** 并填写该 tag。仅推送 tag 不会启动签名。发布请求使用 `github-actions[bot]` 身份启动 tag 工作流，不创建或移动 tag；工作流拒绝版本不一致或不属于 `main` 的 tag。
4. 两个平台均通过后，只有 tag 发布会进入受 `release` 环境保护的 `macos-sign` 任务，等待审核人批准。任务下载并核验已测试制品，不重新编译；先单独给包内 CLI 加上 Developer ID、hardened runtime 和可信时间戳签名，再签署外层应用。应用完成公证并装订票据后，重新生成、签署、公证和装订 DMG。签名检查、Gatekeeper 检查、DMG 与更新包内容一致性检查，以及最终包内 CLI 验收全部通过后，才上传新的已签名 macOS 制品。
5. 随后的受保护 `release` 任务重新核验原始构建来源，并仅接受本次工作流中成功的 `macos-sign` 任务产出的 macOS 压缩包。它核验 GitHub 制品摘要、原始与签名制品的摘要关系、提交及版本后，给最终 macOS 更新包和原有 Windows 安装包生成更新签名、校验和及清单。更新签名不会代替 Apple 公证。
6. 工作流创建包含安装包、已签名更新包、清单和构建来源证明的 **GitHub Release 草稿**，不会自动发布仅构建完成一部分的版本。

所有 Action 固定到完整提交 SHA；checkout 不保留凭据。构建任务只读仓库，签名、发布和构建来源证明所需权限仅分配给对应任务。npm 和 Cargo 依赖使用已提交的 lock 文件。已正式发布的制品不能覆盖修补；应修改源码后发布更高版本。

历史安装包抽样核验确认：**0.1.5、0.1.6 已经过 Apple 公证，Gatekeeper 接受；0.1.9 则是 ad-hoc 签名，没有公证票据，Gatekeeper 拒绝。** 不能笼统称所有早期版本均未公证。当前 0.2.4 的自动发布流程也未接入 Apple 公证；此改动不会修改既有发布制品，需要发布更高版本。Windows 当前仍未配置 Windows 代码签名；NSIS 安装包保留现有状态，并继续执行完整安装冒烟及已安装 CLI E2E。

例如，在已审查且干净的 `main` checkout 中执行：

```sh
git fetch origin main --tags
node scripts/release.mjs validate
release_commit=$(git rev-parse origin/main)
test "$(git rev-parse HEAD)" = "$release_commit" || exit 1
release_version=$(node -p "require('./package.json').version")
release_tag="v${release_version}"
git tag -a "$release_tag" "$release_commit" -m "SAG Wiki $release_version"
git push origin "refs/tags/$release_tag"
gh workflow run request-release.yml --repo Zleap-AI/SAG-Wiki --ref main -f tag="$release_tag"
```

如果 tag 已存在，保持原样，只执行发布请求命令。批准前核对发布任务的发起人为 `github-actions[bot]`。

macOS 的 `.dmg` 用于手动安装，`.app.tar.gz` 用作应用内更新包；Windows 的 NSIS `.exe` 同时用于手动安装和应用内更新。集中签名任务生成 `.sig`，并在受签名保护的注释中绑定发布版本。`requireSignedVersion` 始终开启。

## 复用构建与编译缓存

标签发布优先查找同一仓库、同一工作流、同一提交在 `main` 上成功的 push 构建。版本校验、文档、macOS 和 Windows 各任务最近一次执行必须全部通过，且两个平台的制品仍可用。命中后跳过重复的原始构建和测试；未命中则执行完整构建。查询 API 失败也会回退到完整构建；普通 main 构建不查询复用 API。`main` 缓存始终保存未经 Apple 正式签名与公证的构建制品；无论是否命中缓存，tag 发布都必须执行新的 `macos-sign` 最终签名、公证和验收。

签名前再次核验来源运行和任务结果，按制品 ID 下载压缩包，验证 GitHub SHA256 摘要，再检查包内记录的提交、版本、平台和各文件摘要。签名后的 macOS 制品与原始缓存分开保存，记录原始文件摘要和 Apple 签名信息；集中发布任务核验其来自本次成功的签名任务，并在更新签名前重新核验文件摘要及来源关系。选定后制品过期或丢失会停止发布，可重新运行工作流重新选择或构建。`release` 环境审核和签名版本校验继续执行。

Rust 缓存按 runner 系统/架构、目标平台、Rust 版本、manifest、锁文件及工作流内容隔离，仅可信 `main` push 构建写入。原生测试后保存 debug 缓存并清理 debug 输出，再恢复 release 输出以控制磁盘占用。编译缓存命中仍会执行测试；签名任务不恢复编译缓存，也不缓存密钥。

## 审核并发布草稿

正式发布前，确认两个平台的完整构建与回归、Windows NSIS 安装冒烟检查、包内 CLI E2E 均通过。macOS 还必须通过最终应用及 CLI 的 Developer ID/hardened runtime/时间戳检查、应用与 DMG 的公证和票据校验、Gatekeeper 检查、挂载 DMG 与解压更新包的内容一致性及实际包内 CLI 验收。确认 Release 包含两个平台的更新条目与签名。下载草稿制品，核对 SHA256 校验和及构建来源证明。对已下载的制品可执行：

```sh
gh attestation verify /path/to/downloaded-installer -R Zleap-AI/SAG-Wiki
```

校验和用于确认文件字节一致；来源证明用于确认构建源码和工作流，两者均不能替代更新验签或实际安装检查。托管运行器的冒烟检查不代表所有客户机器均已验收。

有权限的发布审核人检查制品及发布说明后，沿用创建阶段已审核的 `release_tag`。若使用新 Shell，先明确设置为本次审核的标签，不要从可能已经切换版本的工作区重新推导：

```sh
: "${release_tag:?Set release_tag to the reviewed release tag before publishing}"
gh release view "$release_tag" --repo Zleap-AI/SAG-Wiki
gh release edit "$release_tag" --repo Zleap-AI/SAG-Wiki --draft=false --latest
```

正式发布后复核公共安装包链接和更新清单。README 指向最新正式版，下载安装页打开时读取该版本的下载地址和附件实际大小，无需再修改版本配置或提交下载文档 PR。

## 0.1.9 密钥迁移

由于此前的私钥不可用，0.1.9 启用新的更新签名密钥。**0.1.8 及信任旧公钥的更早版本用户，需要手动下载安装一次 0.1.9。** 旧公钥无法验证新私钥签署的更新包；完成这次手动安装后，后续使用新密钥签名的版本即可继续通过应用内更新安装。

| 清单 | 对应客户端 | 行为 |
| --- | --- | --- |
| `latest-v2.json` | 内置新公钥的 0.1.9 及后续版本 | 提供当前版本和新签名。 |
| `latest.json` | 内置旧公钥的客户端 | 逐字保留 0.1.8 原清单、旧下载地址与签名。0.1.8 会显示没有更新；兼容的更早版本仍可能升级到 0.1.8。 |

每次成为最新版本的 Release 均保留旧 `latest.json`，避免旧客户端遇到清单缺失或不可信更新。不能把旧清单版本号改成 0.1.9、替换旧签名或关闭验签。发布说明必须明确旧用户需手动升级一次；保留的旧清单不会通知用户存在 0.1.9。

已有 GitHub 仓库配置无需修改，新二进制会为所配置仓库选择 `latest-v2.json`。自定义 **官网** 更新源仍使用用户填写的完整 URL，不会自动迁移。运营方需使用独立地址提供新清单，并为已迁移客户端更新该设置；需要兼容旧客户端时，同时保留旧通道。

## 失败处理与验证边界

- 缺少签名 Secret、环境保护不足、来源提交混用、平台包缺失、Apple 签名/公证/票据/Gatekeeper 检查失败、最终 macOS 包与来源不符、更新签名损坏或签名版本不一致，均须阻止创建 Release，不能回退到原始 macOS 构建包或未签名更新包发布。
- 有效的新版本清单可能先触发新版通知；客户端仍会在下载、验签阶段拒绝不可信更新包，并保留已安装版本。
- 前端测试覆盖更新进度、失败重试、未保存文档保护和重复点击；原生测试通过本机 HTTP 服务下载已签名夹具，拒绝损坏内容，仅替换临时应用文件。
- Jev E2E 使用真实服务、CLI、配置持久化、索引和检索流程，远端模型由回环地址的协议夹具提供。它验证集成逻辑，不代表真实 Jev 推理质量或远端部署可用性。
- 关闭设置页不会中断更新下载；退出整个应用后，需要重新下载。更新替换程序文件，不主动清除知识库、会话或本地原文件。仍应保留正常用户数据备份，并在正式发布前验证有代表性的升级安装场景。
